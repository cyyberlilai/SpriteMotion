## 修复 α 比例判定把主体内部压成半透明的问题

**问题**：开启「α 比例判定」后，导出的 PNG 帧里 89.6% 的主体内部像素是半透明（平均 α=236.8，皮肤区低到 225.6），叠白底后每通道偏白 7%–12%，整张图发灰发糊。

**根因**：`utils/backgroundRemoval.ts` 的 α 公式 `alpha = dp / max(localMax, tolDist)`，分母取 3×3 邻域最大值，而最大值恒 ≥ 自身 → 只有恰好是邻域最大值的像素才能拿到 255。任何有纹理的表面，绝大多数像素都被系统性压在 255 以下。

**修改**：在 `buildBackgroundMask` 的洪水填充之后、二值化之前新增「边缘带收尾」：
- 新增 `MaskOptions.edgeBand`（默认 3，切比雪夫距离）
- 从 `alpha === 0` 的像素做 BFS 距离场，距背景 > edgeBand 的前景像素一律写回 255
- 仅在 `alphaRatio === true` 时生效；关闭时行为与旧版完全一致

**验证**（用 Downloads 里两张真实导出帧反推原图后重跑）：
- 内部半透明：89.62% → 0.00%，平均 α 236.8 → 255.0
- 半透明像素总数 38514 → 3559，剩下的全在轮廓带内
- 边缘剖面逐像素比对，前 3–4 层过渡值完全不变（未被削平）
- `tsc --noEmit` 与 `vite build` 均通过

**注意**：`edgeBand=3` 覆盖正常软边；若素材是大幅缩小/加过柔光（过渡带 > 6px），需要把 edgeBand 调大到 5–6，否则会削掉部分过渡。用 `edgeBand: 100000` 可复现旧行为，便于 A/B 对比。

## 新增「内部一致性守卫」（`utils/backgroundRemoval.ts:282-336`）

边缘带之后新增 4.6 步：半透明像素若 8 邻域「不透明 + 同色」，回填 α=255。

**判据的两个阈值很关键，试出来的**：
- 邻居"实心"门槛 `SOLID_T` 必须是 **160**，不能用 250。真实误判像素成小片出现，邻域里带着 200~240 的同类伙伴，用 250 时 112 个误判只救回 0~1 个。SOLID_T=160 与 128 效果相同但更保守（低于 160 的邻居自己还在过渡带里）。
- 颜色阈值 `DEFAULT_INTERIOR_GUARD_DIST = 14`，试过 10 → 几乎救不回来（56 个仍误判）。
- 用快照判断邻域、最多跑 2 轮收敛，避免沿半透链扩散。

**验证**：主体内部误判像素 图1 63→1、图2 46→1；改动量仅 79px / 62px；**贴背景（α=0 邻居）的像素 0 个**，即不可能碰到可见轮廓。

**局限**：只修"被邻域压低"的假半透，修不了真正贴着背景 1~2px 的软边；如果还想让轮廓更实，下一步是 band=1 或自适应 band。另外若素材本身含半透明元素（薄纱/光效）且色差小，会被压成不透明 —— 置 `interiorGuard: 0` 可关闭。

## 自适应边缘带宽（已按用户要求回退）

曾实现 `MaskOptions.adaptiveBand`（带宽 = `min(edgeBand, ⌊半宽/2⌋)`，半宽用可分离单调队列求 `2×edgeBand` 半径窗口的最大深度场），验证过窗口最大值与暴力解一致、2048² 性能 113ms→158ms。**但用户实测对生成图片/GIF 没有帮助，已完整回退**，恢复为固定带宽（`distToBg` + `edgeBand` 常量），`adaptiveBand` 选项一并删除。回退后 `tsc --noEmit` 通过。

**回退的理由（值得记住）**：`edgeBand` 是绝对像素量，与结构尺寸无关；对 10~14px 宽的手指，2px 带宽对应的就是真实的 1~2px 抗锯齿过渡，自适应只对半宽 ≤3（≤6px 宽）的结构生效，而这类细结构本来就被内部一致性守卫救到 90%+ 不透明 —— 实测全图半透仅 2751→2749。结论：这类"细结构被啃"的问题不要往带宽上想。

**分析脚本**：`/tmp/sm_analysis/`（adapt.js 含窗口最大值对拍与 A/B；lib.js 是管线模块）。注意用户给的截图**本身就是透明底成品图**（alpha=0 且 RGB=0），dist 计算必须先跳过 `data[i+3]===0`，否则背景会被当成纯黑算成前景。

## 新增「封闭孔洞清理」closedHoleCleanup（方案 A）

**问题**：手与衣领之间、下巴与衣领之间的白色口袋抠不掉。根因不是容差 —— ratio 阶段它们已经是 α≈8，是洪水填充扩散不进去后，被 `if (!visited && alpha<128) alpha=255` 这条兜底规则当成「主体内部白色」救了回来。

**关键难点**：残留白与眼白在像素层面几乎同构（面积 139 vs 147、平均 α 42 vs 54、到纯白 7.4 vs 10.6），任何阈值型 flood fill 都分不开（开口瓶颈 α：口袋 234、眼白 236）。唯一稳定差别是**到真实背景的距离**：口袋 6~7px，眼白超出 17px 采样上限。

**实现**（`utils/backgroundRemoval.ts` 4.4 步，在洪水填充 BFS 之后、兜底规则之前）：
- 距离场种子**只能取 `visited === VISITED_BG` 的像素**。用所有 α=0 当种子会把眼白距离算成 0，直接挖掉眼睛 —— 第一次实现就踩了这个坑，实测左眼白被误删。
- 连通块判据：面积 4~20000 ∧ 平均 α<60 ∧ 到背景距离 ≤ `closedHoleCleanup`（默认 16）。
- `visited` 用位标记：`VISITED_BG=1` / `VISITED_HOLE=2`，兜底规则改成 `!(visited[p] & VISITED_BG)`，省一个 marker 数组。
- 复用洪水填充的 `queue` 做距离场 BFS，不额外分配。

**接线**：`MaskOptions.closedHoleCleanup`、`SpriteConfig.closedHoleCleanup`、`INITIAL_CONFIG` 取 `DEFAULT_CLOSED_HOLE_K`（16，默认开启）、UI 在「保护主体内部颜色」下面加开关 + 4~32px 滑块、`PreviewPlayer`/`gifBuilder`/`frameExporter` 三处补传。

**验证**（用 esbuild 转译真实 TS 后直接调用，与关闭时 diff）：图1 改动 0px、图2 14px、图3 275px（全部变透明）；图3 手间白块 255→130（块内 0），三处眼白/高光全部保持 255 不变；差异图确认绿色像素只在三角口袋内。

## 放大窗撤销（按钮 + 快捷键双通道）

设计取舍：**显眼按钮为主、Ctrl/⌘+Z 为辅**。按钮解决可发现性（误点后第一反应是找按钮，不会去想快捷键），快捷键解决熟练后的效率，按钮上顺带印 `⌘Z`/`Ctrl+Z` 徽标做教学；撤销后弹 1.6s toast「已撤销上一步 · 该选区已取消，恢复到未选择状态」把结果说清楚。

**撤销是帧内作用域**（不是全局栈）：`FrameZoomModal` 里先算出 `pointsInFrame`（按点击顺序、落进本格 rect 的全局索引），撤销时移除该帧最后一个。理由：窗口标题是「帧 N 放大」，用户预期撤回自己刚在这一帧做的事；若用全局 LIFO，在空帧按 Ctrl+Z 会静默删掉别的帧的选区，看起来像坏了。按钮在无本帧选区时 disabled，快捷键则 toast「这一帧还没有选区可撤销」。

## 孤立白点清理（`buildBackgroundMask` 4.8 步）

**成因**：α 比例判定逐像素独立 → 轮廓带 α 锯齿（40/180/92/210 交替）→ 某个 α<128 的像素被不透明邻居围成孤岛 → flood fill 进不去 → 兜底规则 `!visited && α<128 → 255` 把它写成实心，颜色仍是背景色。GIF 只有 1-bit alpha，过渡层被压掉后这粒白点孤立暴露，放大播放特别扎眼。**去色溢出救不了**：纯白像素代入反解公式 `F=(P-(1-c)B)/c` 仍得 255（已用合成用例验证），药不对症。

**实现**：`MaskOptions.whiteSpotCleanup?: boolean`（默认开，不传即开，三条调用路径无需改）。三条判据缺一不可：① 连通块面积 ≤ `WHITE_SPOT_MAX_AREA=3`；② 颜色到 target 距离 ≤ `WHITE_SPOT_COLOR_TOL=48`（最浅肤色实测约 55，留余量）；③ 邻居里有 α=0（才算「长在轮廓上」）。眼白/牙齿同样小同样白，但四周全是皮肤，②③ 都过不了。位置必须在魔术棒（4.7）之后、二值化之前。

**验证**：合成测试在真实素材轮廓上注入 40 个 1~3px 纯白点 → 40/40 全清、0 残留；眼白/牙齿/脸颊/手部 α 完全不变；全图仅改 15px。真实素材（重建白底后）只有「大笑女孩」含 2 个此类点（2px+1px=3px），其余 0 个 —— 说明这些截图边缘本来干净，用户的九宫格动图才有。性能：2048² 关闭 127ms / 开启 122ms，无可测开销。

**若用户的图分辨率更高、白点变成 4~5px**：只需改 `WHITE_SPOT_MAX_AREA`（唯一的旋钮，没做 UI）。

## 反向魔术棒「恢复」（抠多了能补回来）

**前提（关键）**：抠图链路是非破坏性的 —— 每帧 `ctx.getImageData` 从原图重新取，只写回 α，RGB 从未被改写。所以「恢复」不需要猜颜色，把原像素的 α 提回去就是它本来的样子。注意用户截图里的透明像素 RGB 已被导出清零（72205/72205 全是 0），所以**只能对项目内原图恢复，不能对成品图恢复**。

**数据结构改造**：`SpriteConfig.erasePoints` → `editPoints: EditPoint[]`，`EditPoint = {x, y, mode?: 'erase'|'restore'}`（缺省 erase 兼容旧数据）。原 `eraseSeeds` → `MaskOptions.edits`，`mapEraseSeeds` → `mapEditSeeds`（mode 原样带过）。**必须按数组顺序逐个回放**，因为先擦后补 ≠ 先补后擦，用户点按顺序才有确定结果。

**算法**（`selectRestoreRegion`，与 selectMagicWandRegion 并列）：BFS 从种子扩散，两道墙同时成立才继续 —— ① `alpha[q] < 255`（撞实心主体就停）② `distToBg[q] > RESTORE_BG_TOL=32`（撞真背景就停）。夹在这两者之间的就是「被误判成背景的那层皮」。α 按距离给值：`dist≥RESTORE_FULL_TOL(80) → 255`，32~80 线性过渡，避免补出来的边硬切。种子点在纯背景上时会就近 2px 环带吸附。

**UI**：`FrameZoomModal` 加「抠除 / 恢复」segmented 切换（快捷键 X / R），光标 `crosshair` / `copy`。**最有用的设计**：弹窗内跑一遍真实 `buildBackgroundMask`，把「α<128 但原图颜色不是背景色」的像素标**橙色** —— 那就是被误抠的区域，用户照着点即可，不用在棋盘格里猜。主画布 `SpriteCanvas` 上恢复点用绿色双环标记，抠除仍是蓝填充+蚂蚁线。

**验证**：人为把 136px 打成透明（模拟抠多）→ 恢复选区 368px、补回 136px（100%）、误恢复背景 0px、比原状更低 0px、与原状差≤8 的像素 112124/112225。三栏对比图（原状/被抠坏/恢复后）确认轮廓形状还原。

**已知局限**：① 若原图本身带透明通道（用户上传透明底 PNG），那些像素 `data[i+3]===0` 被跳过，无法恢复（没有原始颜色信息）；② 大图每次点击会重跑一遍 `buildBackgroundMask`（帧内像素量级），cropW×cropH 通常几千~几万，可接受。

### 模式区分强化（用户反馈"分不清在抠还是在恢复"）

抠除与恢复共用一个入口「点选修边」，所以**模式必须显式可见**。`editMode: 'erase'|'restore'` 提到 **App 层持有**（不在放大窗里），面板与放大窗改哪边都同步，不会出现"面板显示恢复、窗口实际抠除"的错位。五处视觉锚点：

1. 面板开关下方：两枚等宽按钮「抠除（红）/ 恢复（绿）」，仅 `eraseMode` 开启时出现
2. 主画布右上浮动按钮：颜色红/绿 + 右侧小徽标写当前模式（按钮文字仍为「点选修边」—— 若写成「抠除中」会让人以为在主画布上直接点就生效，实际第一次点击只放大）
3. 主画布顶部提示条：整体底色红/绿 + 图标 + 「按 R / X 切换」
4. 放大窗画布：`ring-2 ring-rose-500 / emerald-500` 彩色外框 + 左上角「抠除中/恢复中」角标
5. 放大窗底部：彩色圆点 + 模式名 + 该模式的操作说明

快捷键 **X = 抠除，R = 恢复**（App 与放大窗都监听，设同一个 state 所以幂等）。

**顺带修掉的连带 bug**：App 的 Esc 监听原本只要 `eraseMode` 开着就生效，导致在放大窗按 Esc 会「关窗口 + 顺手退出整个编辑模式」。改为仅在 `zoomFrame === null` 时接管 Esc（effect 依赖加 `zoomFrame`）。

## 修复「重试」按钮：参数冻结 + 零反馈

- 用户反馈：失败条上的「重试」点了像没作用（注意：按钮叫「重试」，不是「重置」；参数面板右上才是「重置参数」，它不重跑导出）。
- 根因 1（严重）：失败时构造的 `action.onClick` 闭包攥着**失败那一刻的 `handleExportGif`**，里面是当时的 `config`。用户改完参数再点重试，用的还是旧参数 → 依然失败。实测证据：失败后把 rows 3→2，点重试导出 `9帧 234x194`（旧），点主按钮导出 `6帧 234x294`（新）。
- 根因 2：点重试先 `dismissNotice()` 再重跑，若失败是瞬时的（编码器 404），一帧内「关掉→弹出同样的错」→ 像素级无变化，用户看到的就是「点了没反应」。
- 修法：
  1. 新增 `exportHandlersRef`，每次渲染把最新版 `handleExportGif / handleExportFrames` 挂上去；失败条的重试按钮只调 `retryExport(kind)` → 走 ref，永远用当前参数。
  2. `retryExport` 先 `showNotice({pending:true, title:'正在重新导出…'}, null)`（duration=null 表示不自动消失），再执行；`showNotice` 新增 `noticeHoldUntil` 机制，结果若在 650ms 内回来会延后覆盖，保证中间态被看见。
  3. 两个导出函数加 `fromRetry` 参数，从重试进来时不清掉 pending 态。
  4. pending 渲染：`RefreshCw` 转圈替代警告三角，隐藏「重试」与关闭按钮（防连点、防中途关掉）。
- 验证：失败→改 rows 3→2→点重试 → `精灵图_6帧_234x294.gif`（新参数 ✅）；原因未修时点重试 → 依次出现「正在重新导出GIF…」→「GIF 导出失败」（有可见变化 ✅）；重试中无「重试」按钮；重试成功后出现绿色状态条且无残留 alert；成功后可再导出；逐帧 ZIP 同样走 ref（改 rows 后 `精灵图_6帧_234x294.zip`）；1440/390 两宽 pageerror 0；tsc + build 通过。
- 测试踩坑（重要）：Playwright 里 `page.unroute` 必须在 `click('重试')` **之前**，否则重试仍命中 404，会误判成「未修复 / 无下载」。另外「导出失败」用例必须排在首次成功之前（gif.js 已缓存后 route 拦截失效）。

## 修复：智能对齐后，点选修边的抠除/恢复失效

- 现象（用户报告）：在「背景透明化 → 点选修边」里抠掉一块，预览正常；一开「智能对齐」，抠掉的部分又回来了。恢复是否同样？是。
- 复现方法（可靠）：3x3 白底 + 每格蓝方块 → 只保留第 1 帧（剔除 2~9）→ 暂停 → 开透明化 → 放大窗点蓝方块抠除 → 关窗。未对齐时蓝像素 3600→0；开对齐后回到 3600。恢复同理受影响。
- 根因：`mapEditSeeds` 只接受「源矩形 + 缓冲尺寸」，隐含假设「源矩形铺满整个缓冲」。但智能对齐的实际画法是「按内容包围盒裁一小块 → 缩放 → 居中画到 destX/destY」，源矩形和缓冲不再是同一块区域。旧公式把种子点按「整块裁剪区铺满缓冲」换算，落到错误位置 → 魔术棒擦的是背景，主体毫发无损。
- 修法：`mapEditSeeds` 增加可选第 10 参 `dst?: {x,y,w,h}`（源矩形被画到缓冲的哪一块），省略时行为与旧版完全一致（未对齐路径零改动）。三条渲染路径各自的 `drawImage` 旁边记一个 `drawn` 对象（srcX/srcY/srcW/srcH/dstX/dstY/dstW/dstH），再传给 mapEditSeeds：
  - `components/PreviewPlayer.tsx`：未对齐时 drawn = 整块裁剪铺满；对齐且找到 bbox 时改用 bbox 与居中 dest。
  - `utils/gifBuilder.ts`、`utils/frameExporter.ts`：同样处理（导出与预览共用一套映射，避免「预览对了导出错」）。
- 验证：预览 1440 宽，未对齐 3600 → 抠除 0 → 开对齐仍 0 ✅；抠除+恢复互相抵消，对齐前后都是 3600 ✅；导出 GIF（未对齐 194px / 对齐 62px）蓝像素均 0、PNG ZIP 内 frame_000.png 蓝像素 0 ✅；对照组「对齐但不抠除」蓝像素 3600（对齐本身未被破坏）✅；tsc + build 通过。
- 注意：不要再给 SpriteCanvas / FrameZoomModal 传 dst —— 它们画的是未对齐整块，旧默认值就是对的。

## 让「去色溢出」行为与界面一致（关闭 α 比例判定即失效）

- 上一轮体验审计里我写过「Tab 第 3 项是隐藏的 input[type=file]，焦点落到它身上时屏幕上没有任何视觉反馈」。用户要求用截图说明，实测后发现**这句话不成立**。

- 我错在只看 `document.activeElement` 自身（1×1 + `sr-only` 的 `clip: rect(0,0,0,0)` 确实不可见），没把外层 label 的 `focus-within` 算进去。

## 修复：导出 ZIP 时「导出 GIF」误显「生成中」

- 现象（用户报告）：点「导出每一帧 (ZIP)」，旁边的「导出 GIF」显示「生成中 X%」。
- 根因：两个按钮共用同一个 `processingState`，渲染判断只写了 `status === 'rendering'`，没区分是哪一种导出在跑。所以 ZIP 在跑时 GIF 按钮拿到 rendering 状态 → 显示「生成中」；反过来 GIF 在跑时 ZIP 按钮完全没有进度显示（只是变灰），信息也不对等。
- 修法：`ProcessingState` 新增 `renderingKind?: 'gif' | 'zip'`；两个导出函数各自在开始处写入 kind；派生 `gifRendering` / `zipRendering` 两个布尔量，按钮文案与配色按各自的布尔量判断。
- 效果：
  - ZIP 在跑 → 左「导出 GIF」变暗禁用（opacity-40 + cursor-not-allowed），右「打包中 X%」带转圈（之前 ZIP 按钮是没有进度显示的，现在补上了）。
  - GIF 在跑 → 左「生成中 X%」，右「导出每一帧 (ZIP)」变暗禁用。
- 验证：轮询采样（每 50ms）确认 ZIP 点击后 0/50/100ms 分别是 打包中 19/54/81%，GIF 按钮始终是「导出 GIF」disabled；GIF 点击后 0/50ms 是 生成中 0/22%，ZIP 按钮始终是「导出每一帧 (ZIP)」disabled；结束后各自恢复，文件分别为 `t_9帧_234x194.zip` / `.gif`。CPU 降速 12× 抓到两张中间态截图（bar_zip_mid / bar_gif_mid）。tsc + build 通过。
- 改动文件：`types.ts`、`App.tsx`。
