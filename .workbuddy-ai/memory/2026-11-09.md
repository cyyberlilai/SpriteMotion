# 2026-11-09

## SpriteMotion 本地跑起来 + 修复白屏

- 项目：React 19 + Vite 6 + TS，本地 dev server 端口 3000（vite.config.ts 固定）。
- 首次 `npm install` 后 `npm run dev` 可启动，但浏览器打开 localhost:3000 全白。

### 根因
1. `App.tsx` 与 `services/geminiService.ts` 里用了 `process.env.API_KEY`。**Vite 6 在 dev 模式下不应用 `define`**（`vite:define` 插件对 client 环境非 build 直接 return），浏览器没有 `process` 对象 → 抛 `ReferenceError` → 整页白屏。
2. `geminiService.ts` 在模块顶层 `new GoogleGenAI({apiKey: process.env.API_KEY})`，即使 define 生效，无 Key 时也会在导入阶段崩掉。
3. `index.html` 里残留 AI Studio 导出的 `<script type="importmap">`（aistudiocdn.com 指向 react/react-dom），本地已有 node_modules，属于多余且易引入第二份 React。

### 修改
- `vite.config.ts`：删除 `define: {'process.env.*'}`，改用 `envPrefix: ['VITE_','GEMINI_']`。
- `services/geminiService.ts`：改用 `import.meta.env.VITE_GEMINI_API_KEY || import.meta.env.GEMINI_API_KEY`，导出 `GEMINI_API_KEY` / `hasGeminiKey`；`GoogleGenAI` 改为懒加载 `getClient()`，无 Key 时抛中文提示。
- `App.tsx`：`process.env.API_KEY ?` → `hasGeminiKey ?`。
- `index.html`：删除 importmap。

### 验证
- 无头 Chrome（需 `--headless=old --no-sandbox`，新版 headless 在本机沙箱下崩溃）：DOM 正常渲染，截图显示完整深色 UI。
- `npm run build` 通过（557 kB，仅 chunk 体积告警）。

### 已知遗留
- tailwind / gif.js / jszip 走 CDN（cdn.tailwindcss.com、cdnjs），离线或网络受限时样式或导出会失效，后续可改本地依赖。
- 无 `.env.local`，AI 自动识别功能需用户自配 Key。

## API Key 安全性审计（22:11）

用户问：填的 API Key 会不会传到服务器、被记住、留下历史记录。做了完整的代码审计 + 金丝雀测试。

### 代码审计（`grep apiKey` 全部命中点）
只有 3 处：
1. `AiSettingsModal.tsx` — 输入框 value / onChange（纯本地 state）
2. `aiConfig.ts` — localStorage 读写（`spritemotion.aiConfig`）
3. `aiService.ts:122` — `Authorization: Bearer ${resolved.apiKey}` 请求头

全仓 `fetch` 只有 2 处：`gifBuilder.ts`（拉 gif.worker.js CDN）、`aiService.ts`（发往用户配置的 baseUrl）。**没有任何埋点、上报、统计代码**。

| 阶段 | 结果 |
|---|---|
| 输入 Key 过程中 | **新增网络请求 0 个** |
| 点击「保存」时 | **新增网络请求 0 个** |
| 全量扫描所有请求 URL/body/header 含 Key | **0 条命中** |

| 点「自动识别」后 | 只发往**用户自己配置的 baseUrl**，无第三方中转 |

### 存储位置
- `localStorage['spritemotion.aiConfig']`：**是**（明文 JSON）
- `sessionStorage` / `cookie` / `URL` / `console`：**否**

### 需要向用户说明的风险（已写入回复）
1. **localStorage 是明文**，任何能访问该浏览器的人/脚本都能读到；共用电脑不安全。
2. 一旦 XSS 或恶意浏览器扩展存在，localStorage 可被读取。
3. 请求发往用户配置的 baseUrl，**Key 会出现在该厂商服务器的日志里**（这是必然的）。
4. 用「自定义兼容端点」填了别人的中转地址 = 把 Key 交给那个中转方。
5. 浏览器 DevTools 的 Network 面板能看到请求头里的 Key。
6. 「清除已保存的 Key」按钮会 `localStorage.removeItem`，但**已发出的请求在对方服务器日志里删不掉**。

## 已知问题（用户明确说暂不修）：对齐辅助线位置不准（11-10 08:43 诊断）

`PreviewPlayer.tsx` 里两条辅助线是**写死的装饰**，不跟随精灵实际位置：
- 中线：`<div className="w-full h-[1px] bg-red-500 absolute">`（容器正中）
- 底部线：`<div className="w-full h-[1px] bg-indigo-400 absolute bottom-3">`

实测偏差（1440×1000，64×64 帧）：

| 场景 | 线到精灵实际底部 |
|---|---|
| 对齐生效 + 正方形帧 | 1px（碰巧对） |
| 透明化关闭（对齐失效） | **227px** |
| 非正方形帧 64×32（object-contain 留白） | **164px** |
| 线到预览框视觉底边 | 恒定 **14px**（p-3 的 12px 内边距 + 1px 边框） |

**根因**：线用 `absolute bottom-3` 定位，12px 是从内边距盒算的；而 `p-3` 内边距也正好 12px，两个独立值巧合相等才看起来对。真正的对齐位置在 `destY = canvasHeight - bboxH * scale`，辅助线从未读取它。

**若要修**：把辅助线画进 canvas 位图内（随位图一起缩放，永不偏移），或用 `destY` + bbox 反推 CSS 位置。

## 绿色"朦胧"问题定位 + 背景改透明（11-10 10:41）

用户问：「我的绿色和参考站的绿色是同一个吗？为什么我的看着不明亮、有点朦胧？」

### 排查过程（重要方法论）
1. 计算样式：两边文字色**完全相同** `rgb(74,222,128)`，字号 12px、字重 400 都相同。
2. 差异在容器：参考站 `bg transparent` + 无边框；我们 `bg-green-900/25` + `border-green-800`。
3. 截图采样最亮绿像素：参考站 `rgb(74,222,128)`（满值），我们 `rgb(68,207,121)`（约 92%）。
4. 怀疑 `-webkit-font-smoothing: antialiased` → 临时改 `auto` 重采样，**无变化**（headless 本就用灰度抗锯齿），排除。
5. 怀疑字体（Archivo vs 系统字体）→ 临时替换字体重采样，**峰值仍相同**，排除。
6. 隔离测试「透明背景」→ 峰值不变，但**整体观感**变了。

**最终结论**：色值没问题，是「绿字压在深绿半透明底 + 深绿边框」上，色相相同只靠明度区分，色彩冲击被削弱；加上按钮面积大，远看是一块发灰的绿斑 → 这就是"朦胧"的来源。

### 改动
顶栏 AI 已配置态：
```
bg-green-900/25 text-green-400 border-green-800 hover:bg-green-900/40
→
bg-transparent text-green-400 border-transparent hover:bg-slate-800/70
```
实测：文字 `rgb(74,222,128)`、背景 `rgba(0,0,0,0)`、边框 `rgba(0,0,0,0)` —— 与参考站一致。
保留 hover 中性灰底（`bg-slate-800/70`），保证仍看得出可点击。

**教训**：判断"颜色不一样"不能只看 CSS 色值，要采样实际渲染像素；而且**容器背景会显著改变同一颜色的观感**，绿色文字尤其忌用绿色底。

## 更正：参考站的绿色徽章其实有背景（11-10 10:49）

**上一轮判断错误。** 之前探测用的是 `el.closest('button')`，取到的是参考站徽章的**父容器**（透明），误以为参考站是裸绿字。这次逐层扒 DOM 才发现真身：

```html
<span class="px-2 py-1 rounded bg-green-900/30 text-green-400 text-xs border border-green-800">
```

参考站徽章**有绿底 + 绿边框**，只是尺寸小：
| | 参考站 | 我们（改前） |
|---|---|---|
| 背景 | `rgba(20,83,45,0.3)` | `rgba(20,83,45,0.25)` |
| 圆角 | **4px** | 6px |
| 内边距 | **4px 8px** | 6px 10px |
| 高度 | **26px** | 32px |
| 图标 | **无** | KeyRound 12px |

所以"朦胧"的真正来源不是有背景，而是**按钮偏大**（32px vs 26px）——绿色区域面积大，视觉上更糊。

### 最终改动（完全对齐参考站 span）
```
px-2 py-1 rounded text-[12px] leading-4 border
bg-green-900/30 text-green-400 border-green-800 hover:bg-green-900/50
```
- 去掉 KeyRound 图标（参考站无图标），并清理未使用的导入
- 加 `leading-4` 让高度精确到 26px

实测：文字 `rgb(74,222,128)`、背景 `rgba(20,83,45,0.3)`、边框 `1px rgb(22,101,52)`、圆角 `4px`、内边距 `4px 8px`、尺寸 **103×26** —— 与参考站 span（96×26）仅宽度差 7px（因文字更长）。

**方法论教训**：探测样式要精确到目标元素本身，用 `closest()` 容易取到父级；父级和子级的背景/边框可能完全不同。
